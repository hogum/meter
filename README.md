# 电表采集与用电看板

基于 Cloudflare Workers、D1 和 ECharts 的轻量用电监测平台。定时采集电表读数，按住户展示历史用电、余额及状态推测，并通过企业微信群机器人发送业务提醒。

## 功能

- 账号与密码登录，JWT Cookie 会话，按账号绑定的电表隔离数据。
- 定时采集、失败重试、主键去重，以及采集失败记录展示。
- 功率与余额曲线、预设或自定义区间统计、充值估算和余额预计可用时间。
- 基于自适应房间基线（`status.base_line`，点击“近 7 天”自动计算最优功率阈值与判定窗口）推测有人或无人，历史看板与实时通知共用同一套状态机。
- 有人、无人、低余额及充值群通知，按房间配置接收地址。
- 厂商手动上报、历史数据 TXT 和 JSONL 导入、TXT 导出，以及手动历史数据清理。

> 有人状态属于启发式推测；余额预计可用时间和充值金额属于估算。当前没有开放注册、同比环比或峰谷分析，Webhook 失败不自动补发。

## 技术与目录

后端使用 Workers 原生能力，不依赖第三方运行时 npm 包；D1 保存 `users`、`data`、`status` 三张业务表。看板数据由服务端注入 HTML，浏览器通过 CDN 加载 ECharts 绘图。

```text
.
├── src/                Worker 入口、路由、采集、统计、鉴权与通知
├── public/             看板页面
├── db/                 建表、迁移和演示账号 SQL
├── example.env         本地调试环境变量模板
├── wrangler.jsonc      部署配置、数据库绑定和采集计划
└── README.md
```

本目录可单独作为 GitHub 仓库根目录。以下命令均在本 README 所在目录执行，需要 Node.js、npm 和 Cloudflare 账号；Wrangler 通过 `npx` 调用，无需单独安装。

## 配置项

以下环境变量与 Secret 在 Cloudflare Worker 控制台的 Variables and Secrets（或本地 `.env`）中配置：

| 变量 | 类型 | 用途 |
| --- | --- | --- |
| `METERS` | 普通变量 | 允许采集、上报和历史导入的表号列表 |
| `SOURCE_URL` | 普通变量 | 定时采集使用的上游设备详情地址 |
| `RECHARGE_URL` | 普通变量 | 充值页面地址，跳转时自动带上当前电表的 `no` 参数（兼容 `#/` 哈希路由）；未配置时隐藏按钮 |
| `JWT_SECRET` | Secret | JWT 会话签名密钥 |
| `UPLOAD_TOKEN` | Secret | `/api` 上报和历史导入凭证 |
| `WH_<房间号>` | Secret / 变量 | 对应房间的企业微信群机器人地址（按上游返回的房间名匹配，未配置则不推送） |

配置说明：

- **`METERS` 格式**：用英文逗号分隔单个表号和范围，表号须为纯数字，例如 `12345678,12345680-12345682`。范围包含两端，须按升序填写且起止位数（前导零）一致（如 `0010-0020`），重复表号只处理一次，每段范围最多包含 10,000 个表号。
- **定时采集与 `SOURCE_URL`**：`wrangler.jsonc` 默认每两分钟触发一次定时采集（`triggers.crons`），启用时须配置 `SOURCE_URL`；若仅使用 `/api` 手动上报，可移除 `triggers.crons`。
- **环境变量保留**：`wrangler.jsonc` 已开启 `keep_vars: true`，部署时会保留控制台设置的普通变量；`users` 表决定住户账号的登录授权。

## 获取企业微信 Webhook 地址

1. 打开企业微信电脑端，在需要接收通知的群中进入“管理聊天信息”。
2. 选择“消息推送”→“自定义消息推送”（旧版入口可能显示“群机器人”）。
3. 填写名称等信息，创建后复制页面提供的完整 Webhook 地址；已有推送可由创建者查看详情获取。
4. 在 Cloudflare Worker 的运行时 Variables and Secrets 中添加对应房间的变量，例如 `WH_A101`，值填刚复制的完整地址。

定时采集按上游返回的房间号匹配 `WH_<房间号>`，优先取 `houseName`，为空时取 `userName`；手动上报使用表单里的 `room`。缺少房间号或对应 Webhook 时只记录采样。实际地址不要提交到 GitHub。

参考：[企业微信官方消息推送配置说明](https://developer.work.weixin.qq.com/document/path/99110) · [腾讯云获取步骤图解](https://cloud.tencent.com/document/product/1759/128391)

## 本地预览与演示账号（可选）

### 本地试运行

把 `example.env` 复制为同目录下的 `.env`，填入采集地址、表号列表和本地登录用的签名密钥，然后启动：

```sh
npx wrangler dev
```

本地状态与云端数据分离。测试真实住户账号时，需要单独初始化本地表、账号与样本，不会自动下载云端数据。

### 演示账号（`demo`）

默认账号和密码均为 `demo`。本地试运行时先初始化本地库并导入演示账号：

```sh
npx wrangler d1 execute meter --local --file db/init.sql
npx wrangler d1 execute meter --local --file db/seed-users.sql
```

- **云端演示与提示**：若需在云端开放演示，在已执行 `db/init.sql` 的远程库上把第二条命令中的 `--local` 改为 `--remote` 即可；若不启用线上演示，可删去 `public/dashboard.html` 登录页里的演示账号提示。
- **认证与数据隔离**：登录统一通过 `users` 表认证；认证成功后，系统根据账号名是否为 `demo` 选择演示数据源，`serial_no` 不参与该判断。模拟数据本身不写入 D1；若配置了 `RECHARGE_URL`，看板仍保留充值按钮展示，`/recharge` 和 `/clean` 接口对 `demo` 账号返回 403 拒绝操作。
- **模拟行为**：演示看板和 TXT 导出共用最近 30 天的模拟数据，固定每 3 分钟一个样本。模拟租客白天可能外出，傍晚回家、夜间留宿，周末晚起；睡眠期间保留家电基础负载；余额随用电扣减并在低位模拟充值，有人状态使用默认基线推测。
- **固定场景与基线**：demo 固定模拟暖季低待机房间，统一使用默认基线 `DEFAULT_BASE_LINE = '12w/15m'`（不对 demo 执行自动寻优），不按当前月份切换季节，也不根据有人判定结果反向修补数据：
  - 基础待机约 `7.8–10.2 W`，活动时段叠加照明及设备负荷，睡眠时段包含暖季空调负荷。
  - 空调与热水器共用 `26–32°C` 的日内/多日环境温度日程。
- **热水器模型**：按样本特征模拟连续冷却与用水补热（简化物理模型，非实测水温或流量）：
  - 散热系数对应约 `30 W` 平均热损、`250 Wh` 温控回差、约 `2050 W` 电热管，按 `15 秒` 步长积分并处理采样槽内开关时刻。
  - 无人保温补热间隔通常约 `8–10 小时`（每次约 `0.25 kWh`），受环境温度影响有小幅漂移；洗澡用水会提前触发并延长加热。
  - 模型先迭代求得稳态初值，再输出 `35 天（5 周）` 连续循环（覆盖最长 30 天查询），家电与电热管功率按实际叠加。

## 部署与更新

### 首次部署到全新账号或空数据库

先创建新 D1，并把返回的数据库 ID 替换写入 `wrangler.jsonc` 中的 `database_id`（绑定名保持 `DB`），同时配置好运行时变量、Secret 和可用域名（`wrangler.jsonc` 默认 `workers_dev: false`；若全新账号未绑定自定义域名或路由，可在控制台绑定域名，或将 `wrangler.jsonc` 的 `workers_dev` 设为 `true`）：

```sh
npx wrangler d1 create meter
# 将返回的 database_id 填入 wrangler.jsonc 后再执行建表：
npx wrangler d1 execute meter --remote --file db/init.sql
```

`db/init.sql` 只创建 `users`、`data`、`status` 三张表。随后添加住户账号并执行 `npx wrangler deploy`，后续数据由定时采集或厂商上报写入。登录页默认带有 `demo` 演示提示，若线上保留该提示，可在远程库执行 `npx wrangler d1 execute meter --remote --file db/seed-users.sql` 导入演示账号。

### 更新现有云端项目

如果已经部署过名为 `meter` 的 Worker 并绑定了现有 `meter` D1 数据库，常规更新代码时保留数据库绑定即可，无须重新建库、导入本地数据或运行初始化 SQL；若涉及表结构或配置格式变更，按文末“重大更新日志”处理（例如 `npx wrangler d1 execute meter --remote --file db/20261108.sql`）。

安装 Node.js 与 npm 后登录 Cloudflare，再部署：

```sh
npx wrangler login
npx wrangler deploy
```

已有可用登录或 API Token 时按现有鉴权方式使用即可。部署会上传后端与静态页面，并应用配置中的绑定及每两分钟一次的采集计划；数据库中的业务记录由 D1 独立保存。

> `wrangler.jsonc` 当前设置 `workers_dev: false`，访问应以 Cloudflare 控制台中已启用的域名或路由为准，部署返回地址不一定表示 `workers.dev` 入口已开放。

### GitHub 自动部署

把本目录的内容上传为 GitHub 仓库后，在 Cloudflare 控制台选择现有 `meter` Worker，进入 Settings → Build，连接仓库并选择生产分支。使用 Workers Builds 即可，无需额外编写 GitHub Actions。

| 设置 | 值 |
| --- | --- |
| 根目录 | 仓库根目录，保留默认值（若上传包含 `code/` 的完整仓库，则设为 `code`） |
| 构建命令 | 留空 |
| 部署命令 | `npx wrangler deploy` |

控制台 Worker 名须与 `wrangler.jsonc` 中的 `name` 一致，之后推送生产分支即可触发构建部署。Webhook 地址应在 Worker 的运行时 Variables and Secrets 中设置，不要提交到 GitHub 仓库。

官方说明：[Workers Builds](https://developers.cloudflare.com/workers/ci-cd/builds/) · [构建配置](https://developers.cloudflare.com/workers/ci-cd/builds/configuration/) · [Secrets](https://developers.cloudflare.com/workers/configuration/secrets/)

## 添加住户账号

管理员在项目目录打开终端（PowerShell 或 Bash），替换下面的账号、初始密码和表号，再执行命令写入线上 `meter` 数据库（同命令也可用于重置密码或更换绑定表号，对应登录页“忘记密码请联系管理员”）：

```sh
npx wrangler d1 execute meter --remote --command "INSERT OR REPLACE INTO users (user, pw, serial_no) VALUES ('住户账号', '初始密码或哈希', '实际表号');"
```

- `user`：填写唯一的账号名，避免使用空格；英文字母不区分大小写。
- `pw`：填写临时密码或本系统支持的加盐 PBKDF2 哈希（`pbkdf2-sha256$` 前缀保留给哈希格式）。临时明文密码可能留在终端历史中，首次登录验证成功后会在 D1 中自动替换为随机加盐的哈希。
- `serial_no`：填写住户实际电表的编号并保留前导零。需要定时采集时，将该表号加入 `METERS`。

字段值中的单引号写成两个单引号（在 PowerShell / Bash 中若密码含 `$` 或双引号，请注意对应 shell 的引号转义，或优先使用单引号哈希后写入）。写入成功后，住户即可在登录页使用该账号和密码登录。

测试本地账号时，把命令中的 `--remote` 改为 `--local`；空的本地库先执行 `npx wrangler d1 execute meter --local --file db/init.sql` 建表。

## 上游采集接口

Worker 对 `SOURCE_URL` 发起 GET 请求，并通过查询参数 `SerialNo` 传入 `METERS` 中的表号，例如 `GET /device-detail?SerialNo=12345678`。上游应返回 HTTP 200 和如下 JSON（示例数据均为虚构）：

```json
{
  "success": true,
  "response": {
    "serialNo": "12345678",
    "lastOnlineTime": "2026-11-17 12:00:00",
    "readNumber": 1234.56,
    "residualAmount": 78.9,
    "valveState": 0,
    "valveStateName": "合闸",
    "areaId": 100001,
    "houseName": "A101"
  }
}
```

- `serialNo`：表号字符串，应与请求的 `SerialNo` 一致。房间名优先取 `houseName`，为空时取 `userName`。
- `lastOnlineTime`：东八区的 `YYYY-MM-DD HH:mm:ss` 格式，最多超前当前时间 300 秒。
- `readNumber`：累计电量（kWh），须为有限非负数字；`residualAmount` 为剩余电费（元），使用 JSON 数字。
- `valveState` / `valveStateName`：`valveStateName` 为 `null` 时该条采样会被跳过（JSONL 导入同样跳过）；`valveState`（如 `0` 合闸、`1` 断闸）用于看板顶部阀门状态徽章配色。
- `areaId`（可选）：存在时用于将 `,"areaId":` 后的不变字段拆出压缩存储。

## 请求入口

| 方法与路径 | 说明 |
| --- | --- |
| `GET /` | 登录页或当前住户看板 |
| `POST /login`、`POST /logout` | 登录与退出 |
| `GET /export` | 按当前所选区间（支持与看板相同的 `range` 或 `from`/`to` 参数，默认近 `24h`）导出当前账号绑定电表的成功记录（TXT） |
| `GET /recharge` | 登录后跳转到配置的充值页面 |
| `GET /api?act=up&tk=xxx` | 打开历史数据上传页 |
| `POST /api?act=up&tk=xxx` | 提交实时读数或导入 TXT、JSONL 历史数据 |
| `GET /clean` | 登录后在浏览器地址栏直接访问触发，手动删除当前电表 90 天前的采样，保留账号及状态；无页面按钮，不自动执行 |

### 实时上报与历史导入

GET 和 POST 都通过查询参数 `tk` 校验 `UPLOAD_TOKEN`。实时上报在 POST 表单中提交 `no`（表号，须在 `METERS` 中）、`kwh`（累计读数）和 `balance`（余额），可选传入 `room`（用于记录房间号并匹配 `WH_<房间号>` 通知）。服务端使用接收时间，跨秒重复请求由调用端控制。

```sh
curl -d 'no=12345678&kwh=1234.56&balance=78.9' 'https://example.com/api?act=up&tk=xxx'
```

历史导入可使用上传页，也可直接用 `multipart/form-data` 提交 `file` 字段，文件须使用 UTF-8 编码且不超过 16 MiB：

- **TXT**：可直接上传 `/export` 的导出文件，其中包含厂商 JSON 原文和以 `manual` 开头的 CSV 记录。
- **JSONL**：每行一个厂商成功响应对象，例如 `{"success":true,"response":{"serialNo":"12345678","lastOnlineTime":"2026-11-06 12:00:00","readNumber":1234.56,"residualAmount":78.9}}`。

导入保留原采样时间，同一电表同一时间的成功记录会跳过，失败记录可补齐；页面返回写入和跳过条数。导入文件中的所有表号均须在 `METERS` 中（`demo` 账号导出的模拟记录表号为 `demo`，不可直接用于 `/api?act=up` 导入）。导入静默补齐历史，实时状态和通知由后续采集或上报推进。

## 核心机制与技术细节

### 1. 状态表结构与原文去重压缩

- **前后半段拆分存储**：厂商上游 JSON 在 `,"areaId":` 之后的部分（设备型号、区域、单价等）长期不变。入库时 `data.raw` 仅保存前半段变化字段，后半段存入 `status.tail`；仅当 `tail` 变化时 `status` 表才 `INSERT` 新行，否则原地 `UPDATE` 最新状态行，导出时按时间区间拼接还原完整原文。
- **`status` 关键字段**：
  - `broke`：低余额标记（`0` = 余额正常，`1` = 低于预警线）。实时采集或上报时，余额 `< 2` 元置 `1` 并触发低余额预警（回升至 `>= 2` 元后重置）；单次采样余额增加 `> 1` 元触发充值通知。
  - `base_line`：`"Ww/Mm"` 格式的房间基线配置（如 `17w/33m`、`100w/23m`，缺失时回退默认 `12w/15m`），代表基线功率阈值 `W` 瓦与无人回落判定窗口 `M` 分钟。
  - `last_kwh`：最近一次成功采样的累计电量读数，实时采集时直接结合 `last_online_time` 计算增量，无需读取 `data` 表。
  - `delta` 与 `duration`：单步状态机只使用离散阶段码 `delta`（`0–7`，按历史看板分类顺序分段）和单一阶段计时器 `duration`（秒）。遇到无效 `delta` 时保留当前有人/无人状态，并按阶段 `0`、`duration = 0` 重新累计（若该步同时因断档或读数回退被判为 `broken`，无人侧按 `winSec` 作为保守起始）：

| `delta` | 阶段含义 | `duration` 计时内容 | 历史看板分类 |
| --- | --- | --- | --- |
| `0` | 静默 | 有人时累计静默；无人时累计跳字等待 | 静默 |
| `1` | 基线内正增量 | 有人时累计静默；无人时清零 | 静默 |
| `2` | 加热后观察 | 无人时累计加热结束后的静默观察时间 | 静默 |
| `3` | 低底噪待确认短静默 | 累计包含短静默的活动确认时间 | 活动 |
| `4` | 活动 / 活动待确认 | 无人时累计确认时间；有人时清零 | 活动 |
| `5` | 疑似加热前沿 | 无人时累计连续高功率加热时间 | 热水器 |
| `6` | 热水器主步 | 无人时累计连续加热；有人时保留静默倒计时 | 热水器 |
| `7` | 热水器尾步 | 无人时保存保守等待时间；有人时保留静默倒计时 | 热水器 |

### 2. 跨采样有效功率与有人/无人状态机

状态推进仅依赖上一状态与当前步采样，主要规则如下：

- **量化跨度折算**：电表最小分辨率为 `0.01 kWh`（10 Wh）。若上一步为普通正增量（`delta = 4` 或 `1`）或尾步后出现 `>= 0.02 kWh` 普通增量，跳字跨度 `span` 取本步间隔 `gap`；否则用当前阶段的 `duration` 近似等待时间（低底噪短静默 `delta = 3` 取 `max(182, duration - 182)`）再加 `gap`，据此计算有效功率 `effW = d × 3600000 / span`。
- **热水器脉冲确认**：主步阈值以 `182 秒` 内 `0.09 kWh` 为基准，采样间隔更长时按比例放大；紧跟主步且增量低于主步阈值的正增量记为尾步（`delta = 7`）。
  - **无人时**：连续主步累计加热达到 `720 秒` 才确认有人（首步最多计 `182 秒`）。
  - **有人时**：主步和尾步均保留静默倒计时（主步首步最多回拨 `364 秒`），防止短时保温重置离家倒计时。
- **加热前后沿保护（`delta = 5` / `2`）**：覆盖稀疏或跨槽采样拆开的保温脉冲：
  - **进入前沿（`delta = 5`）**：无人时，若单步平均功率 `>= 1200 W` 但增量未达到完整主步阈值，以下情况先转入 `5` 观察（从当前步重计加热时间，首步最多 `182 秒`）：① 处于活动待确认（`delta = 4` 或 `3`，不延续此前活动计时）；② 处于静默（`delta = 0`）且满足低底噪常规间隔（`gap <= 273 秒`）或已静默至少 `900 秒`。
  - **前沿推进与退回**：连续高功率（`>= 1200 W`）累计达到 `720 秒` 确认有人；达到主步阈值转为 `delta = 6`；功率回落后若有正增量则转为尾步 `7`（不把加热时间并入活动确认），无增量则进入加热后观察 `2`。
  - **尾步后保护与停机观察**：尾步 `7` 之后若出现至少 `0.02 kWh` 普通增量，直接按本步间隔估算功率；单次 `0.01 kWh` 仍按尾步保守跨度折算。加热后静默进入 `delta = 2` 观察 `900 秒` 后回到 `0`，观察期后的单次 `0.01 kWh` 不直达唤醒，需由后续连续活动确认。
- **低底噪唤醒（`baseW <= 40 W`）**：无人时需满足 `effW > max(1.4 × baseW, 20 W)`。单步 `0.01 kWh` 在 `span <= 915 秒` 且 `span < min(36000 / baseW, winSec)` 时可直接确认有人（前一步为 `7`、`1` 或 `2` 时除外）；其余情况首步最多计 `182 秒`，累计有效活动达到 `300 秒` 确认。确认期间的短静默只要当前阶段的估计跨度（`max(182, duration - 182) + gap`）小于 `36000 / max(1.4 × baseW, 20 W)` 秒，即可经由 `delta = 3` 延续并计入确认时长。有人时活动维持阈值为 `baseW`。
- **高底噪唤醒（`baseW > 40 W`）**：无人时超过 `baseW` 的首步最多计 `182 秒`，后续连续有效活动按实际间隔累计达到 `540 秒` 确认；遇到零增量即结束本次待确认。
- **离家回落与断档容忍**：有人时，基线内采样累计静默达到 `winSec = M × 60` 秒即回落为无人。常规间隔上限为 `915 秒`（为约 15 分钟采样预留 15 秒抖动余量）；在 `915–2700 秒`（45 分钟）内，若整段平均功率不高于 `baseW`，仍计入静默。超出容忍条件或读数回退时，实时状态保留原有人/无人值并重置计时，历史看板将该点记为未知状态。

### 3. 近 7 天基线自动寻优

- **底噪下界估计**：查看预设“近 7 天”时，`computeOptimalBaseline` 将热水器主步与尾步的增量视为零，以 `2 小时` 滑窗、`30 分钟` 步长统计平均功率（有效窗口至少覆盖 `90 分钟`），取第 15 百分位 `P15` 计算功率下界：`minBaseW = max(12, ceil(P15 × 1.25))`。
- **候选网格与回放**：候选功率由 `minBaseW` 与 `k = 2..16` 个采样间隔对应的量化台阶 `ceil(36000 / (k × (182 - 2)))` 组成（当 `minBaseW` 落在某台阶 `[floor(36000 / (k × 182)), baseW)` 区间内时移出 `minBaseW`，避免贴边误唤醒），并分别搭配 `5、9、15、23、33 分钟` 窗口回放。若当前配置功率 `>= minBaseW`，也保留当前配置（含非网格窗口）一并参与评分。
- **评分与更新**：回放中将两次状态翻转间隔 `< 45 分钟` 记为短片段，将 `915–2700 秒` 内因平均功率超基线而被判为断档的间隔计入断档秒数，按以下公式取最低分配置（无额外切换门槛；仅当基线变化时回写 `status`，样本不足时沿用已有基线）：

```text
score = 短片段数 × 10 + (翻转次数 + 断档秒数 / 182) × 1.2 + 窗口分钟数 × 0.35 + (候选功率 - minBaseW) × 0.1
```

### 4. 历史看板回溯校准与 20 分钟平滑曲线对齐

- 看板功率曲线使用 `20 分钟`（`1200 秒`）滑动窗口平滑 `0.01 kWh` 量化锯齿，仅用于视觉展示。
- 历史序列在采样断档或读数回退后进入未知状态，直到重新确认有人，或基线内的连续采样达到无人判定窗口。
- 历史分析（`src/modules/history-occupancy.js`）复用 `stepOccupancy`：确认有人后，将段首连续的待确认活动采样（含低底噪短静默）回填为有人；段尾直接采纳状态机的无人确认结果（确认前的静默等待仍计入有人时段）。
